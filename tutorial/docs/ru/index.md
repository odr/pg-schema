# Учебник по pg-schema

[`pg-schema`](https://hackage.haskell.org/package/pg-schema) — это библиотека
для работы с PostgreSQL из Haskell, в которой правильность запросов
проверяет компилятор. От других библиотек её отличают две идеи:

- **Описание схемы берётся из самой базы**, поэтому оно не может незаметно
  разойтись с ней. Генератор один раз читает живую базу PostgreSQL и
  записывает Haskell-модуль, в котором на уровне типов описаны её таблицы,
  колонки, ключи и связи.
- **SQL-запрос не пишется, а строится по Haskell-типам и проверяется по сгенерированному описанию схемы.** Вы описываете, какие
  данные нужны — какие поля и какие связанные строки по внешним ключам, — и
  получаете один SQL-запрос, который читает ровно это. Вставка и обновление
  устроены так же — по типу входных данных.

Опечатка в имени колонки, связь не с той таблицей, значение не того типа,
вложенные данные не той формы — всё это становится ошибкой компиляции, а не
ошибкой при выполнении запроса. А когда схема базы меняется, достаточно
перегенерировать модуль, и компилятор покажет все места в программе, которые
нужно поправить.

## Как работать с pg-schema {#how-you-work-with-pg-schema}

Вся работа состоит из четырёх шагов. Для каждого шага дана ссылка на
соответствующий файл учебника, чтобы было видно, как это выглядит в
настоящем проекте.

1. **Создаём базу данных.** Схема задаётся в PostgreSQL как обычно — SQL-
   скриптом или миграциями. pg-schema не создаёт и не меняет таблицы.
   Схема учебника:
   [`tutorial/sql/00-create-schema.sql`](https://github.com/odr/pg-schema/blob/master/tutorial/sql/00-create-schema.sql). В её
   комментариях указаны имена внешних ключей: в pg-schema связь между
   таблицами называется по имени её FK-констрейнта.
2. **Генерируем описание схемы.** Небольшая программа — генератор — читает
   метаданные PostgreSQL и записывает Haskell-модуль с описанием таблиц,
   колонок, ключей, связей и перечислений на уровне типов. Генератор:
   [`tutorial/app/generator/Main.hs`](https://github.com/odr/pg-schema/blob/master/tutorial/app/generator/Main.hs),
   сгенерированный модуль: [`tutorial/app/app/Sch.hs`](https://github.com/odr/pg-schema/blob/master/tutorial/app/app/Sch.hs).
   Генератор перезапускается после каждого изменения структуры базы.
3. **При желании описываем структуры данных.** Обычные записи с
   `deriving Generic`, поля которых названы по колонкам и связям, —
   например, [`Project` и `Task`](https://github.com/odr/pg-schema/blob/master/tutorial/app/app/Tut/Wow.hs). Инстансы не нужны.
   Можно обойтись и вовсе без записей: поля описываются прямо в типе
   операции с помощью `PgTag` (`"title" := Text :. "status" := …`).
4. **Описываем запросы на EDSL со статической проверкой.** `selectSch`,
   `insertSch`, `insertJSON`, `upsertJSON`, `updateByCond`, `deleteByCond` и
   другие получают аннотацию со сгенерированной схемой и базовой таблицей.
   По типам входных данных и результата pg-schema строит SQL, а компилятор
   сверяет каждое имя, тип, допустимость `NULL` и связь с описанием из шага 2.
   Примеры — главы этого учебника и их код в
   [`tutorial/app/app/Tut`](https://github.com/odr/pg-schema/blob/master/tutorial/app/app/Tut).

Когда база меняется, достаточно повторить шаг 2, и компилятор покажет все
запросы, которые с ней больше не согласуются.

## Пример {#an-example}

Вот полный пример: что лежит в базе, что генерируется и что пишете вы.

**База данных (шаг 1).** В примере участвуют две таблицы учебной схемы
`tut` — проекты и их задачи, — связанные внешним ключом, которому PostgreSQL
дал имя `tasks_project_id_fkey` (скрипт целиком:
[`00-create-schema.sql`](https://github.com/odr/pg-schema/blob/master/tutorial/sql/00-create-schema.sql)):

```sql
create type project_status as enum ('draft', 'active', 'archived');

create table projects (
  id          bigserial primary key,
  owner_id    bigint not null references users(id),  -- projects_owner_id_fkey
  title       text not null,
  status      project_status not null default 'draft',
  ...
);

create table tasks (
  project_id  bigint not null references projects(id), -- tasks_project_id_fkey
  seq         integer not null,
  title       text not null,
  priority    integer not null default 100,
  ...
  primary key (project_id, seq)
);
```

**Сгенерировано (шаг 2).** Модуль [`Sch`](https://github.com/odr/pg-schema/blob/master/tutorial/app/app/Sch.hs) вы не пишете и
не правите: его создаёт генератор по базе. Он экспортирует тип схемы `Sch` и
Haskell-тип для каждого перечисления, здесь — с конструкторами
`Project_status_draft`, `Project_status_active` и `Project_status_archived`.

**Написано вами (шаги 3 и 4).** Это весь пользовательский код примера,
вместе с расширениями и импортами:

```haskell
--8<-- "app/app/Tut/Why.hs:why-header"
--8<-- "app/app/Tut/Why.hs:why-imports"

--8<-- "app/app/Tut/Why.hs:why-ann"

--8<-- "app/app/Tut/Why.hs:why-select"
```

Откуда берутся имена:

| Имя | Откуда |
|-----|--------|
| `Sch`, `Project_status_active` | сгенерированный модуль `Sch` |
| `Ann`, `RenamerId`, `->>`, `:=`, `selectSch`, `qRoot`, `qWhere`, `qPath`, `=?`, `<?` | библиотека, модуль `PgSchema.DML` |
| `:.`, `Connection` | `postgresql-simple` (`:.` реэкспортируется из `PgSchema.DML`) |
| `MyAnn`, тип результата, запрос | ваш код |
| `"projects"`, `"title"`, `"status"`, `"priority"`, `"tasks_project_id_fkey"` | имена из базы; компилятор сверяет их с `Sch` |

`MyAnn` — аннотация, общая для всех операций: `Sch` — сгенерированное описание
схемы, `"tut" ->> tab` — таблица в схеме базы `tut`, `RenamerId` означает, что
имена в программе совпадают с именами в базе, а `5` ограничивает глубину
вложенности связей. Связь проектов с их задачами называется по внешнему
ключу, `tasks_project_id_fkey`; с помощью ренеймера связям и колонкам можно
дать и привычные имена в camelCase. Подробно всё это разбирается в главе
[«Рабочая модель pg-schema»](02-core-workflow.md).

Шаг 3 — описание структур данных — необязателен, и в этом примере его нет:
тип результата записан прямо в сигнатуре полями `PgTag` (`"title" := Text`,
а `:.` соединяет поля в строку). Здесь это проекты со списком их задач. Ниже
то же самое сделано с обычными записями. `qRoot` задаёт условия для корневой
таблицы `projects`, а `qPath` — для ветки задач. Вот что вернёт этот запрос на
учебных данных:

```text
--8<-- "out/tutorial.txt:why-select"
```

Весь результат читается одним SQL-запросом, который `pg-schema` строит сама:

```sql
--8<-- "out/tutorial.txt:why-select-sql"
```

А если опечататься в имени колонки и написать `"priorty"`, программа не
скомпилируется, и компилятор перечислит все колонки таблицы:

```
• In schema Sch
  for table "tut" ->> "tasks"
  name "priorty" is not defined.

  Valid values are:
    Fields: project_id, seq, title, priority, payload, watchers.
    Foreign key constraints: tasks_project_id_fkey, task_events_project_id_seq_fkey.

  Your source or target type or renamer is probably invalid.
```

Такие запросы легко делать сколь угодно сложными. Форму результата — какие
таблицы, через какие связи и с какими полями — задаёт тип, а условия,
сортировку и ограничения можно добавить к любой его ветке. По этому описанию
строится один SQL-запрос, который читает всё дерево сразу. На практике такие
запросы соединяют два десятка таблиц и больше. Написать такой SQL вручную
очень трудно, а склеивать его из кусочков в коде трудно поддерживать. Здесь
сложность и безопасность работают вместе: чем больше запрос, тем ценнее то,
что каждое имя и каждый тип в нём проверены компилятором.

Наконец, для чтения и записи строк данных не нужны никакие инстансы — ни
`FromRow`/`ToRow`, ни `FromJSON`/`ToJSON`. Достаточно вывести `Generic` или
описать поля через `PgTag`. (Инстансы понадобятся только собственным типам
значений внутри колонок, например типу, который хранится в `jsonb`.) Поэтому
легко использовать параметризованные структуры данных. Большие похожие
структуры в разных местах программы часто требуют разных полей: например, для
списка проектов нужны только названия, а для подробной карточки — ещё
владелец и задачи. Вместо двух почти одинаковых типов можно завести один,
параметризованный контекстом, а ненужным в данном контексте полям дать тип
`()` (`If` берётся из `Data.Type.Bool`, а `==` — из `Data.Type.Equality`):

```haskell
--8<-- "app/app/Tut/Why.hs:why-param"
```

Оба вызова `selectSch` в `whyParam` выглядят одинаково: что именно читать,
`pg-schema` определяет по типу результата, а он задан сигнатурой. Поля типа
`()` не читаются вовсе. Для `Project 'List` запрос сводится к выборке
названий из одной таблицы `projects`, без соединения с пользователями и без
подзапроса для задач. Для `Project 'Details` из базы приходят и владелец (это
одна строка: внешний ключ ведёт из проекта к пользователю), и список задач.
Лишнего из базы не вытаскивается, а тип остаётся один.

## Производительность

О скорости работы `pg-schema` заботится с самого начала. Главное здесь —
количество обращений к базе: дерево данных читается одним запросом и
записывается одной операцией, вместо множества отдельных запросов к связанным
таблицам, каждый из которых — отдельный обмен с сервером. На практике именно
это даёт основной выигрыш.

Проверки на уровне типов не бесплатны для компилятора, и этому тоже
уделялось много внимания. На схеме примерно из 50 таблиц и запросах,
соединяющих два десятка таблиц и больше, время компиляции остаётся
приемлемым. Большую базу можно описать несколькими схемами `Sch`. Заметнее
всего нагрузка видна по HLS: он потребляет больше памяти, чем в проектах без
вычислений на уровне типов, но для работы в реальных проектах это приемлемо.

## Другие библиотеки

Среди библиотек для типобезопасной работы с базой из Haskell есть, например,
opaleye, beam и persistent. В них схема базы описывается в коде на Haskell, а
запросы собираются из выражений встроенного языка, что позволяет записать
почти любой запрос. `pg-schema` устроена иначе. Как сказано в начале, описание схемы
берётся из самой базы, а запрос строится по типу результата. Для сложных деревьев данных это
короче и надёжнее, а для того, что так не выразить, остаётся выход в
произвольный SQL. Что касается hasql, это альтернатива не `pg-schema`, а
`postgresql-simple`, поверх которого `pg-schema` работает.

## Требования {#requirements}

- GHC ≥ 9.10: библиотека использует видимые аргументы типов
  (`selectSch (MyAnn "users") …`). Включать для этого расширение
  `RequiredTypeArguments` в своём коде не нужно. Tutorial проверяется на
  GHC 9.12.4 (см. `cabal.project` в корне репозитория).
- PostgreSQL и `psql`/`createdb` в `PATH`.
- Расширения GHC. Примеры написаны на `GHC2024`, в который уже входят
  `DataKinds` и `TypeApplications`. Дополнительно нужны:
    - `OverloadedStrings` — для строковых значений (`Text`) в данных и
      условиях. Имена таблиц, полей и связей (`"title"`, `MyAnn "users"`)
      от него не зависят: это литералы уровня типов (`Symbol`);
    - `BlockArguments` — для `qRoot do …` и `qPath "…" do …`;
    - `TypeFamilies` и `UndecidableInstances` — для своего ренеймера;
    - `DuplicateRecordFields` — если у нескольких record-типов есть
      поля с одинаковыми именами (например, `title` у проекта и задачи).

## Перед стартом

Понадобятся запущенный PostgreSQL, GHC с cabal (см. требования выше) и
клон репозитория `pg-schema`: в нём лежат примеры учебника. В своём проекте
достаточно подключить пакет `pg-schema` с Hackage. Всё остальное — создание учебной базы, генерация
схемы и запуск примеров — описано в главе [«Быстрый старт»](01-wow.md).
Примеры лежат в `tutorial/app`, SQL-скрипты — в `tutorial/sql`, а главы — в
`tutorial/docs`.
