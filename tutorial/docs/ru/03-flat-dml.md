# Изменение данных в одной таблице

В этой главе мы разберём, как изменять данные с помощью `pg-schema`: вставлять,
изменять и удалять строки одной таблицы, а также изменять и вставлять строки
«по ключу». Об операциях, которые одним запросом затрагивают сразу несколько
связанных таблиц, рассказывает глава
[«Изменение связанных данных»](05-tree-dml.md).

Как и в предыдущей главе, мы используем аннотацию `MyAnn` с ренеймером
`MyRenamer`, поэтому поля можно называть в стиле camelCase, а данные описываем
с помощью `PgTag`. Все примеры этой главы лежат в
`tutorial/app/app/Tut/FlatDml.hs` и выполняются после примеров главы 02, на тех
же данных.

Для работы с одной таблицей в `pg-schema` есть пять групп операций:
`insertSch` вставляет строки, `updateByCond` изменяет строки, подходящие под
условие, `deleteByCond` удаляет их, а `updateByKey` и `upsertByKey` изменяют
или вставляют строки, найденные по первичному или уникальному ключу. У всех
операций, кроме удаления, есть вариант с подчёркиванием в конце имени
(`insertSch_`, `updateByCond_` и так далее), который ничего не возвращает из
базы. Как и при чтении, SQL каждой операции определяют типы: колонки, которые
мы записываем, берутся из типа входных данных, а колонки в `returning` — из
типа результата.

## Вставка

С `insertSch` и `insertSch_` мы уже встречались в предыдущей главе. Вставим с
их помощью два проекта и попросим базу вернуть их идентификаторы. Чтобы не
повторять `"поле" =: значение` в каждой строке, воспользуемся функцией `named`:
она получает список имён полей один раз и приписывает их значениям каждой
строки по порядку.

```haskell
--8<-- "app/app/Tut/FlatDml.hs:insert-projects"
```

```text
--8<-- "out/tutorial.txt:insert-projects"
```

??? note "SQL, отформатированный для чтения"

    ```sql
    --8<-- "out/tutorial.txt:insert-projects-sql"
    ```

`named` возвращает ровно те же строки, что получились бы с `(=:)`, просто их
короче записывать. Значения при этом берутся как есть: конструктор
`Project_status_active` или `Nothing` не нужно оборачивать. Если число имён не
совпадёт с числом значений в строке, программа не скомпилируется.

С результатом мы поступили наоборот: `plains @("id" := Int64)` убирает имена
полей и оставляет только значения, поэтому в выводе — просто список
идентификаторов. Тип, переданный `plains`, одновременно задаёт и тип
результата `insertSch`, а значит, и колонки в `returning`. Так мы будем
поступать и в остальных примерах этой главы.

Колонки `id` и `created_at` во входных данных не указаны, их заполняют
значения по умолчанию. Зато все обязательные колонки, то есть объявленные как
`NOT NULL` и не имеющие значения по умолчанию, во входных данных быть
обязаны, и это проверяется при компиляции. Если, например, забыть `title`,
программа не соберётся:

```
• We can't insert data because not all mandatory fields are present.
  Table: NameNS "tut" "projects"
  Missing mandatory fields: '["title"]
```

Та же ошибка появится и в том случае, если в таблицу добавят новую
обязательную колонку, а мы перегенерируем `Sch.hs`: компилятор покажет все
места, где вставляются строки в эту таблицу.

:mag: Колонка `tags` — это массив `text[]`. Для массивов в `pg-schema` есть
свой тип `PgArr`. В отличие от `PGArray` из `postgresql-simple`, его инстанс
`ToField` знает тип элементов в базе, поэтому вставлять можно массивы любых
типов. Элементы `PgArr` имеют тип `Maybe`, как и элементы массивов в
PostgreSQL, а функция `pgArr'` строит массив из значений без `Nothing`.

## Изменение по условию

`updateByCond` записывает одни и те же значения во все строки, подходящие под
условие. Переведём второй проект в архив и попросим вернуть изменённые строки. Тип
перечисления `project_status` нам понадобится не раз, поэтому заведём для него
синоним:

```haskell
--8<-- "app/app/Tut/Common.hs:project-status"
```


```haskell
--8<-- "app/app/Tut/FlatDml.hs:update-by-cond"
```

```text
--8<-- "out/tutorial.txt:update-by-cond"
```

Первый аргумент после соединения — новые значения, второй — условие. Условия
здесь те же, что и в запросах на чтение, и проверяются так же: подробно они
разобраны в главе [«Select»](04-select.md). Если нужно только число изменённых
строк, подойдёт `updateByCond_`.

Сама `updateByCond` возвращает только строки из `returning`. Посмотреть на её
SQL можно с помощью `updateText`, которому нужны те же типы и то же условие:

```haskell
--8<-- "app/app/Tut/FlatDml.hs:update-text"
```

```text
--8<-- "out/tutorial.txt:update-text"
```

??? note "SQL, отформатированный для чтения"

    ```sql
    --8<-- "out/tutorial.txt:update-text-sql"
    ```

В списке параметров здесь только значение из условия. Новые значения
колонок `updateText` не получает, а `updateByCond` подставляет их перед
параметрами условия, на места первых знаков `?`.

Имена колонок в новых значениях проверяются так же, как и везде. Опечатка
`"status1"` вместо `"status"` даст знакомую ошибку:

```
• In schema Sch
  for table "tut" ->> "projects"
  name "status1" is not defined.

  Valid values are:
    Fields: id, owner_id, title, status, tags, created_at.
    Foreign key constraints: projects_owner_id_fkey, tasks_project_id_fkey.

  Your source or target type or renaimer is probably invalid.
```

## Изменение по ключу

Часто нужно изменить не все строки, подходящие под условие, а несколько
конкретных строк, причём каждую по-своему. Для этого есть `updateByKey`. Он
принимает список записей, в каждой из которых есть ключ строки и новые
значения, и для каждой записи выполняет `update` по этому ключу. Ключом
может быть первичный ключ или уникальный ключ таблицы, и какой из них
использовать, `pg-schema` определяет по полям записи. В примере ниже это
первичный ключ `id`:

```haskell
--8<-- "app/app/Tut/FlatDml.hs:update-by-key"
```

```text
--8<-- "out/tutorial.txt:update-by-key"
```

??? note "SQL, отформатированный для чтения"

    ```sql
    --8<-- "out/tutorial.txt:update-by-key-sql"
    ```

Строки с `id = 999` в таблице нет, и `updateByKey` ничего не вставляет.
Поэтому результат имеет тип `[Maybe r]`: для каждой входной записи — либо
изменённая строка, либо `Nothing`, если строки с таким ключом не нашлось.
Сам тип `r` при этом остаётся обычным, без `Maybe`. Важно, что результаты
гарантированно идут в том же порядке, что и входные записи, и их ровно
столько же. Поэтому каждый `Nothing` легко сопоставить с записью, для которой
строка не нашлась: например, с помощью `zip` входного списка и результата. Обратите внимание и на
`IS NOT DISTINCT FROM` в условии: так ключ совпадает и тогда, когда в нём есть
`NULL`, что важно для уникальных ключей из nullable-колонок.

Если в записи нет ни одного полного ключа, изменить строку не по чему, и
программа не скомпилируется. Компилятор перечислит ключи, которые можно
использовать:

```
• We can't upsert data because for table NameNS "tut" "users"
  not all mandatory fields are present and no full primary or
  unique key is covered by record fields.
  Missing mandatory fields: '[]
  Possible keys: ['["id"], '["email"]]
```

## Вставка или изменение по ключу

`upsertByKey` вставляет строку, а если строка с таким же ключом уже есть,
изменяет её. В SQL это `insert … on conflict (ключ) do update`. Поскольку
строка может оказаться новой, в записи должны быть все обязательные колонки,
как для `insertSch`, и, кроме того, полный ключ, по которому определяется
конфликт. Обновим пользователя с `id = 3` и вставим нового с `id = 100`:

```haskell
--8<-- "app/app/Tut/FlatDml.hs:upsert-by-pk"
```

уникальный ключ по `email`, и если в записи нет `id`, но есть `email`,
конфликт определяется по нему:

```haskell

```

```text

```

??? note "SQL, отформатированный для чтения"

    ```sql
    --8<-- "out/tutorial.txt:upsert-by-uk-sql"
    ```

Пользователь с адресом `quentin@example.com` уже был, поэтому изменилось
только его имя, а `id` остался прежним. Новая пользовательница «Mia» получила
`id = 5`, а не 4: при конфликте PostgreSQL успел взять следующее значение
последовательности для `id` до того, как обнаружил конфликт, и это значение
пропало. Так ведёт себя любой `insert … on conflict`, и на работу программы
это не влияет.

Запись, в которой есть только ключ, `upsertByKey` не примет: вставить такую
строку нельзя, потому что не хватает обязательных колонок.

```
• We can't insert data because not all mandatory fields are present.
  Table: NameNS "tut" "users"
  Missing mandatory fields: '["name"]
```

Для изменения строки по одному лишь ключу используйте `updateByKey`.

## Какую операцию выбрать

Если строки заведомо новые, подойдёт `insertSch`. Если строки уже есть и их
нужно изменить по ключу, причём отсутствие строки — не повод её создавать,
нужен `updateByKey`. Если строки может не быть и тогда её нужно создать,
нужен `upsertByKey`, и в записи должны быть все обязательные колонки. Наконец,
`updateByCond` и `deleteByCond` работают не с отдельными строками, а со всеми
строками, подходящими под условие. Какие типы допустимы в `returning` у каждой
операции, сведено в таблицу в [приложении](appendix-reference.md#returning).

## Мини-checklist после главы

- [ ] Строки вставляются через `insertSch`, а `named` позволяет не повторять
      имена полей в каждой строке.
- [ ] Тип результата (например, переданный `plains`) задаёт колонки в
      `returning`.
- [ ] `updateByCond` и `deleteByCond` работают со всеми строками, подходящими
      под условие.
- [ ] `updateByKey` возвращает `Nothing` для ненайденных ключей, в том же
      порядке, что и вход.
- [ ] `upsertByKey` требует все обязательные колонки и полный ключ.
