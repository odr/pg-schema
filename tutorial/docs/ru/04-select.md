# Select

В этой главе мы подробно разберём чтение данных. Мы уже знаем, что форму
результата `selectSch` задаёт тип: какие поля читать, какие связанные таблицы
подтягивать и вложены ли они списком или одной строкой. Здесь мы посмотрим,
какие формы результата бывают, а потом перейдём к описанию запроса: условиям,
переходам по связям, сортировке, ограничению числа строк, агрегатам и, наконец,
к запасному выходу на случай, когда возможностей `pg-schema` не хватает.

Обратите внимание, что `Owner` — не record, а `PgTag`:
`type Owner = "name" := Text`. Две нотации можно свободно смешивать. Поле
Generic-рекорда может быть строкой `PgTag`, её списком или `Maybe`, а рекорд,
наоборот, может быть частью цепочки `:.`, как в главе 02. Для маленькой
строки из одного-двух полей отдельный record заводить не обязательно.

По SQL видно, как `pg-schema` строит такой запрос. Родительская строка
присоединяется через `join`, а дочерние строки собираются подзапросом в
JSON-массив, так что весь результат читается одним запросом.

Если внешний ключ допускает `NULL`, родителя может и не быть. Тогда поле
должно иметь тип `Maybe`, а вместо `join` используется `left outer join`.
Хороший пример — колонка `users.manager_id`: она ссылается на ту же таблицу
`users`. По одному и тому же внешнему ключу можно пройти в обе стороны: к
начальнику (одна строка или `Nothing`) и к подчинённым (список). Направление
`pg-schema` определяет по типу поля, а ренеймер позволяет дать обоим полям

## Условия

Условия задаются функцией `qWhere` внутри `qRoot`. Для сравнения с параметром

— `~=?` (`like`) и `~~?` (`ilike`). Условия соединяются операторами `&&&` и
`|||`, а `pnot` их отрицает. `&&&` связывает сильнее, чем `|||`, так же как
`and` и `or` в SQL, поэтому лишние скобки не нужны:

Здесь мы выбрали активные проекты, в названии которых есть «site», и, кроме
того, неактивные проекты с `id` 3 или 4. `pinArr` проверяет, что значение

Типы значений в условиях проверяются так же строго, как и поля результата.
Если колонка допускает `NULL`, значение в сравнении тоже должно быть `Maybe`.
Например, `"managerId" =? (1 :: Int64)` не скомпилируется:

```
• You have to use Maybe for nullable fields

  Table: NameNS "tut" "users"
  DB Field name: "manager_id"
  DB Field type: NameNS "pg_catalog" "int8"
  Haskell Field type: Int64
```

Правильно писать `"managerId" =? Just (1 :: Int64)`. Заметьте, что в сообщении
стоит имя `manager_id`: имена в условиях, как и поля результата, проходят
через ренеймер, поэтому писать их можно и в camelCase, и так, как они названы
в базе.

## Ветки результата: qPath

Условия, сортировка и ограничение числа строк задаются не только для корневой
таблицы, но и для любой ветки результата. Для этого служит `qPath` с именем
связи: внутри него все указания относятся уже к таблице на другом конце
связи. В следующем примере мы берём только активные проекты, сортируем их по
названию в обратном порядке, а у каждого проекта оставляем одну задачу — с
наибольшим приоритетом среди тех, у которых приоритет меньше 50 (`ascf` и
`descf` задают сортировку по полю по возрастанию и по убыванию):

```haskell

```

```text

```

??? note "SQL, отформатированный для чтения"

    ```sql
    --8<-- "out/tutorial.txt:sel-path-sql"
    ```

Условия на ветку попадают в подзапрос, который собирает задачи, и поэтому
влияют только на содержимое списка задач, но не на то, какие проекты попадут в
результат. Проект без подходящих задач останется в результате с пустым
списком. Так ведут себя дочерние ветки. С веткой-родителем всё иначе: родитель
присоединяется через `join`, поэтому условия, заданные в `qPath` к нему
(например, `qPath "projectOwner"`), попадают в `where` основного запроса и
отбирают уже строки корня.

!!! warning "Условия ветки привязаны к полю результата"
    Как мы видели в главе 01, условия, сортировка и ограничения из `qPath`
    применяются к полю результата с тем же именем связи. Если такого поля в
    типе нет, они молча не попадут в запрос. Для ветки-родителя это значит,
    что вместе с полем из типа пропадёт и отбор строк корня.

Разница между `pchild`/`pparent` и `qPath` важна. `pchild` и `pparent`

`pparent`. Удобно сначала решить, какие строки нужны в корне, а потом
отдельно настроить содержимое дочерних веток.

## Связь таблицы с самой собой

Для внешнего ключа, который ссылается на свою же таблицу, `qPath` не годится.
Направление `qPath` определяет по связи: ведёт ли она из текущей таблицы или в
неё. У связи `users_manager_id_fkey` верно и то и другое, и по имени нельзя
понять, идём мы к начальнику или к подчинённым. (В типе результата такой
неоднозначности нет: там направление видно по типу поля — список или одна
строка.) Компилятор об этом скажет:

```
• qPath cannot be used for self-reference relation.
  Use qPathFromHere or qPathToHere.

  Table: NameNS "tut" "users"
  Relation: "users_manager_id_fkey"
```

Вместо `qPath` здесь используются `qPathFromHere` (по ключу из текущей строки,
то есть к начальнику) и `qPathToHere` (к строкам, которые ссылаются на
текущую, то есть к подчинённым). Выберем пользователей без начальника или с
начальником `id = 1`, а в списке подчинённых оставим только тех, в чьём имени
есть буква «o»:

```haskell
--8<-- "app/app/Tut/Select.hs:sel-self-path"
```

??? note "SQL, отформатированный для чтения"

Подчинённый Боба Дейв в списке не оказался: в его имени нет буквы «o».

Имена `manager` и `subordinates` здесь — лишь два имени одного внешнего
ключа, и направление задаёт не имя, а функция. Если бы мы написали
`qPathFromHere "manager"` с тем же условием, оно относилось бы к начальнику и,
как у любой ветки-родителя, отбирало бы самих пользователей: остались бы
только те, у кого в имени начальника есть «o». На наших данных таких нет, и
результат был бы пустым.

## Агрегаты

Агрегатные функции тоже задаются типом результата. Поле типа
`Aggr' ACount Int64` превращается в `count(*)`, а `Aggr' AMax Int32` —
в `max` по колонке с именем поля. Остальные поля без агрегатов становятся
ключами группировки, и `group by` добавляется автоматически:

??? note "SQL, отформатированный для чтения"

`Aggr'` предназначен для запросов с группировкой: в каждой группе есть хотя бы
одна строка, поэтому `max` по обязательной колонке не может вернуть `NULL`, и
`Maybe` не нужен. Если же группировки нет, а таблица пуста, `max` вернёт
`NULL`. Для таких запросов служит `Aggr`: у всех функций, кроме `count`, он
требует `Maybe`. Компилятор не запрещает использовать `Aggr'` и без
группировки, но тогда запрос к пустой таблице упадёт при чтении результата,
поэтому без группировки лучше всегда брать `Aggr`:

## jsonb и массивы

Колонку типа `jsonb` можно читать в любой тип с инстансами `FromJSON` и
`ToJSON` из `aeson`. Там, где значения разбирает или передаёт сам
`postgresql-simple`, нужны ещё `FromField` (чтение в корне запроса) и

данные этой главы). Проще всего определить их через `fromJSONField` и
`toJSONField`. Колонка `tasks.payload`
хранит оценку задачи:


## Запасной выход: UnsafeCol, pUnsafeCond и UnsafeOrd

На `pg-schema` можно записать многое, но не всё. Обидно, когда большой запрос
к двум десяткам таблиц не ложится в схему из-за того, что в одном условии
нужно сравнить сумму двух полей. Для таких случаев есть «небезопасные»
средства: они позволяют вставить в запрос кусок SQL, а всё остальное
по-прежнему проверяет компилятор. `UnsafeCol` описывает поле
результата как произвольное SQL-выражение: в типе указываются колонки,
которые подставляются вместо знаков `?`, само выражение и тип результата.
Знаки `?` здесь означают именно колонки, а не параметры запроса. Имена колонок
проверяются, а вот выражение и соответствие его результата типу (`Int32`) —
нет: ошибка в них обнаружится только при выполнении. `pUnsafeCond` задаёт
условие как произвольный текст, а `UnsafeOrd` — выражение для сортировки
вместе с её направлением. Оба строят текст в небольшой монаде `CondMonad`, где
`qual @"поле"` возвращает имя колонки текущей таблицы с правильным
псевдонимом. Имя поля `qual` не проверяет, поэтому опечатка в нём тоже
обнаружится только при выполнении:

```haskell
--8<-- "app/app/Tut/Select.hs:sel-unsafe"
```

```text

```

??? note "SQL, отформатированный для чтения"

    ```sql
    --8<-- "out/tutorial.txt:sel-unsafe-sql"
    ```

Здесь мы выбрали задачи, у которых сумма номера и приоритета больше 40, для
каждой вычислили длину названия и отсортировали задачи по этой длине. За
правильность таких выражений отвечает уже программист, а не компилятор,
поэтому пользоваться ими стоит только тогда, когда обычных средств
действительно не хватает. Значение из программы, как число 40 в нашем
условии, лучше передавать параметром, а не вклеивать в текст: `tell` добавляет
его в список параметров, а в тексте на его месте ставится `?`. Так в запрос не
проберётся SQL-инъекция.

## Мини-checklist после главы

- [ ] Понятно, как тип результата задаёт дочерние списки, родителя и
      необязательного родителя.
- [ ] Условия собираются из операторов `=?`, `~~?`, `&&&`, `|||`, `pnot`,
