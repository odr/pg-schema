# Select

В этой главе мы подробно разберём чтение данных. Мы уже знаем, что форму
результата `selectSch` задаёт тип: какие поля читать, какие связанные таблицы
подтягивать и вложены ли они списком или одной строкой. Здесь мы посмотрим,
какие формы результата бывают, а потом перейдём к описанию запроса: условиям,
переходам по связям, сортировке, ограничению числа строк, агрегатам и, наконец,
к запасному выходу на случай, когда возможностей `pg-schema` не хватает.

По SQL видно, как `pg-schema` строит такой запрос. Родительская строка
присоединяется через `join`, а дочерние строки собираются подзапросом в
JSON-массив, так что весь результат читается одним запросом.

Если внешний ключ допускает `NULL`, родителя может и не быть. Тогда поле
должно иметь тип `Maybe`, а вместо `join` используется `left outer join`.
Хороший пример — колонка `users.manager_id`: она ссылается на ту же таблицу
`users`. По одному и тому же внешнему ключу можно пройти в обе стороны: к
начальнику (одна строка или `Nothing`) и к подчинённым (список). Направление
`pg-schema` определяет по типу поля, а ренеймер позволяет дать обоим полям

## Условия

Условия задаются функцией `qWhere` внутри `qRoot`. Для сравнения с параметром
есть операторы `=?`, `<?`, `>?`, `<=?` и `>=?`, для сравнения строк по образцу
— `~=?` (`like`) и `~~?` (`ilike`). Условия соединяются операторами `&&&` и
`|||`, а `pnot` их отрицает. `&&&` связывает сильнее, чем `|||`, так же как
`and` и `or` в SQL, поэтому лишние скобки не нужны:

```haskell
--8<-- "app/app/Tut/Select.hs:sel-cond"
```

```text
--8<-- "out/tutorial.txt:sel-cond"
```

??? note "SQL, отформатированный для чтения"

    ```sql
    --8<-- "out/tutorial.txt:sel-cond-sql"
    ```

Здесь мы выбрали активные проекты, в названии которых есть «site», и, кроме
того, неактивные проекты с `id` 3 или 4. `pinArr` проверяет, что значение
входит в список. Список может быть и пустым, и тогда условие просто ложно.
Обратите внимание, что колонка `id` в условии есть, хотя в результате её нет:
условия могут ссылаться на любые колонки таблицы.

Отдельного внимания заслуживают колонки, допускающие `NULL`. Проверить, что
значения нет, можно с помощью `pnull`. Для сравнения со значением, которое
само может быть `Nothing`, есть оператор `=??`: он превращается в
`is not distinct from`, и `Nothing` с ним совпадает с `NULL`. Ещё один способ
проверить вхождение в список — `pin`, он принимает непустой список
(`NonEmpty`):

```haskell

```

```text

```

??? note "SQL, отформатированный для чтения"


Типы значений в условиях проверяются так же строго, как и поля результата.
Если колонка допускает `NULL`, значение в сравнении тоже должно быть `Maybe`.
Например, `"managerId" =? (1 :: Int64)` не скомпилируется:

```
• You have to use Maybe for nullable fields

  Table: NameNS "tut" "users"
  DB Field name: "manager_id"
  DB Field type: NameNS "pg_catalog" "int8"
  Haskell Field type: Int64
```

Правильно писать `"managerId" =? Just (1 :: Int64)`. Заметьте, что в сообщении
стоит имя `manager_id`: имена в условиях, как и поля результата, проходят
через ренеймер, поэтому писать их можно и в camelCase, и так, как они названы
в базе.

## Ветки результата: qPath

Условия, сортировка и ограничение числа строк задаются не только для корневой
таблицы, но и для любой ветки результата. Для этого служит `qPath` с именем
связи: внутри него все указания относятся уже к таблице на другом конце
связи. В следующем примере мы берём только активные проекты, сортируем их по
названию в обратном порядке, а у каждого проекта оставляем одну задачу — с
наибольшим приоритетом среди тех, у которых приоритет меньше 50:

```haskell

```

```text

```

??? note "SQL, отформатированный для чтения"

    ```sql
    --8<-- "out/tutorial.txt:sel-path-sql"
    ```

Условия на ветку попадают в подзапрос, который собирает задачи, и поэтому
влияют только на содержимое списка задач, но не на то, какие проекты попадут в
результат. Проект без подходящих задач останется в результате с пустым
списком. Так ведут себя дочерние ветки. С веткой-родителем всё иначе: родитель
присоединяется через `join`, поэтому условия, заданные в `qPath` к нему
(например, `qPath "projectOwner"`), попадают в `where` основного запроса и
отбирают уже строки корня. Как мы видели в главе 01, условия ветки применяются к полю
результата: если такого поля в типе нет, они в запрос не попадут.

## Связь таблицы с самой собой

Для внешнего ключа, который ссылается на свою же таблицу, `qPath` не годится:
по имени связи нельзя понять, в какую сторону мы идём, к начальнику или к
подчинённым. Компилятор об этом скажет:

```
• qPath cannot be used for self-reference relation.
  Use qPathFromHere or qPathToHere.

  Table: NameNS "tut" "users"
  Relation: "users_manager_id_fkey"
```

Вместо `qPath` здесь используются `qPathFromHere` (по ключу из текущей строки,
то есть к начальнику) и `qPathToHere` (к строкам, которые ссылаются на
текущую, то есть к подчинённым). Выберем пользователей без начальника или с
начальником `id = 1`, а в списке подчинённых оставим только тех, в чьём имени
есть буква «o»:

```haskell
--8<-- "app/app/Tut/Select.hs:sel-self-path"
```

```text
--8<-- "out/tutorial.txt:sel-self-path"
```

??? note "SQL, отформатированный для чтения"

    ```sql
    --8<-- "out/tutorial.txt:sel-self-path-sql"
    ```

Подчинённый Боба Дейв в списке не оказался: в его имени нет буквы «o».

Имена `manager` и `subordinates` здесь — лишь два имени одного внешнего
ключа, и направление задаёт не имя, а функция. Если бы мы написали
`qPathFromHere "manager"` с тем же условием, оно относилось бы к начальнику и,
как у любой ветки-родителя, отбирало бы самих пользователей: остались бы
только те, у кого в имени начальника есть «o».

## Запасной выход: UnsafeCol и pUnsafeCond

Не всё, что можно написать на SQL, можно выразить через `pg-schema`. Для
таких случаев есть два «небезопасных» средства. `UnsafeCol` описывает поле
результата как произвольное SQL-выражение: в типе указываются колонки,
которые подставляются вместо знаков `?`, само выражение и тип результата.
Имена колонок при этом проверяются, а вот выражение — нет. `pUnsafeCond`
задаёт условие как произвольный текст. Чтобы сослаться в нём на колонку
текущей таблицы с правильным псевдонимом, используется `qual`:

когда обычных средств действительно не хватает.
