# На практике

В учебных примерах у нас была одна схема базы, все связи были объявлены
внешними ключами, а сама схема не менялась. В настоящем проекте всё сложнее:
таблицы бывают разложены по нескольким схемам PostgreSQL, не каждая связь
оформлена внешним ключом, а структура базы меняется с каждой миграцией. В этой
главе мы посмотрим, как `pg-schema` справляется со всем этим и как встроить
генерацию схемы в процесс разработки и в CI.

Примеры этой главы лежат в `tutorial/app/app/Tut/Practice.hs`, а генератор —
в `tutorial/app/generator/Main.hs`. Перед примерами программа пересоздаёт
схему и добавляет двух пользователей, Alice (`id = 1`) и Bob (`id = 2`).

## Что описывает генератор

Какие таблицы и связи попадут в `Sch.hs`, определяет последний аргумент
`updateSchemaFile` — значение типа `GenNames`. У нашего генератора оно такое:

```haskell
--8<-- "app/generator/Main.hs:gen-names"
```

В `schemas` перечисляются схемы базы, все таблицы которых нужно описать. Если
из какой-то схемы нужны только отдельные таблицы, их можно перечислить в
`tables` полными именами, например `["billing" ->> "invoices"]`. Связи между выбранными таблицами генератор находит сам по внешним
ключам, а в `addRelations` можно добавить связи, которых в базе нет. Обо всём
этом по порядку.

## Несколько схем базы

В учебной базе кроме схемы `tut` есть схема `audit` с журналом изменений
проектов:

```sql
--8<-- "sql/00-create-schema.sql:audit"
```

Раз обе схемы перечислены в `GenNames`, таблица `audit.project_log` описана в
том же `Sch.hs`, что и остальные. Аннотация для неё отличается от `MyAnn` из
главы [«Рабочая модель pg-schema»](02-core-workflow.md) только схемой базы в имени таблицы, поэтому заведём для неё такой же
синоним и, как `MyAnn`, будем передавать его операциям первым аргументом:

```haskell

## Связи, которых нет в базе

Иногда связь между таблицами есть по смыслу, но не объявлена внешним ключом.
Так бывает с представлениями (у них внешних ключей не бывает вовсе), с
секционированными таблицами, со старыми базами или когда внешний ключ
сознательно не заводят, например из-за нагрузки. В учебной базе так устроена
колонка `task_events.author_id`: она хранит `id` пользователя, но внешнего
ключа на `users` у неё нет.

Такую связь можно описать в генераторе через `AddRelation`, как в `GenNames`
выше: имя связи, таблица, из которой она ведёт, таблица, в которую она ведёт,
и пары колонок. После этого `pg-schema` работает с ней так же, как с внешним
ключом. В типах результата и в `qPath` её имя, как обычно, проходит через
ренеймер: `"taskEventsAuthor"`. Там же, где связь задаётся полным именем вместе
со схемой, как в `pchild` и `pparent` из главы [«Select»](04-select.md), вместо схемы базы
указывается `_add`: все добавленные связи генератор помещает в это
пространство имён. Пример с `pparent` будет чуть ниже.

Добавим задачи с событиями. Колонка `author_id` — обычная колонка, и мы
заполняем её значениями, а у одного события намеренно укажем несуществующего
пользователя 99:

```

В документации `GenNames` (её фрагмент есть в главе [«Рабочая модель pg-schema»](02-core-workflow.md)) про добавленные связи
сказано «Be careful!». База ничего о них не знает и не проверяет: в
`author_id` может оказаться `id` несуществующего пользователя, как у события
`(2, 2)`, и автор просто не найдётся.
Компилятор проверит, что запросы соответствуют описанию связи, но за то, что
описание соответствует данным, отвечаете вы.

## Когда схема меняется

Самое полезное свойство `pg-schema` проявляется тогда, когда структура базы
меняется. Возьмём для примера миграцию, которая переименовывает колонку и
добавляет обязательную:

```sql
--8<-- "sql/migration-example.sql"
```

Колонка `code` добавляется без значения по умолчанию, поэтому такая миграция
пройдёт только на пустой таблице, как в нашей учебной базе сразу после
`make tut-db-init`. В настоящей базе понадобилось бы значение по умолчанию
или заполнение колонки, но для `pg-schema` это ничего не меняет: важно лишь,
что колонка обязательна.

После того как миграция применена, нужно перегенерировать `Sch.hs`:

```bash
psql "$PG_CONN" -f tutorial/sql/migration-example.sql
cabal run tutorial:generator
```

Генератор перезапишет файл, а `git diff` покажет, что именно изменилось в
описании базы. Предыдущая версия сохраняется в `Sch.hs.bak` и перезаписывается
при каждой генерации, так что этот файл стоит добавить в `.gitignore`. Если
описание базы не изменилось, файл не трогается, а вывод генератора
детерминирован, поэтому ложных изменений в `git diff` не бывает. Теперь
достаточно собрать проект, и компилятор перечислит все места, которые
миграция сломала. На учебном проекте таких ошибок 42, в пяти модулях. Вот
две из них. В главе [«Изменение данных в одной таблице»](03-flat-dml.md) мы вставляли проекты без колонки `code`:

```
• We can't insert data because not all mandatory fields are present.
  Table: NameNS "tut" "projects"
  Missing mandatory fields: '["code"]
```

А в главе [«Select»](04-select.md) условие использовало колонку `priority`, которой больше нет:

```
• In schema Sch
  for table "tut" ->> "tasks"
  name "priority" is not defined.

  Valid values are:
    Fields: project_id, seq, title, weight, payload, watchers.
    Foreign key constraints: tasks_project_id_fkey, task_events_project_id_seq_fkey.

  Your source or target type or renamer is probably invalid.
```

Без `pg-schema` каждая из этих ошибок обнаружилась бы только при выполнении
соответствующего запроса — в тестах, если они его покрывают, или уже в
работе. Здесь же компилятор сразу показывает полный список мест, которые
нужно исправить, и пока он не пуст, программа не соберётся.

Чтобы вернуть учебную базу в исходное состояние, достаточно снова выполнить
`make tut-db-init` и `cabal run tutorial:generator`.

Отсюда важное практическое правило: генератор должен быть отдельной
программой (в нашем проекте — отдельным исполняемым компонентом cabal),
которая не зависит от `Sch.hs`. Иначе после миграции, пока `Sch.hs` не
перегенерирован, не соберётся и сам генератор. Запускать его нужно из того
каталога, относительно которого указан путь к `Sch.hs`, у нас — из корня
репозитория.

## Проверка в CI

Остаётся убедиться, что `Sch.hs` в репозитории не отстаёт от схемы базы:
кто-то мог добавить миграцию и забыть перегенерировать файл. Для этого
пригодится результат `updateSchemaFile`: он возвращает `True`, если файл
пришлось создать или изменить. Наш генератор принимает флаг `--check` и в
этом случае завершается с ошибкой. Вот он целиком (первый аргумент
`updateSchemaFile` включает подробный вывод):

```haskell
--8<-- "app/generator/Main.hs"
```

В CI достаточно поднять базу (например, сервис PostgreSQL в контейнере),
применить к ней все миграции тем же инструментом, которым вы пользуетесь в
проекте, задать `PG_CONN` и запустить генератор с этим флагом. Если `Sch.hs`
устарел, генератор завершится с ошибкой, и сборка не пройдёт. Заодно он
перезапишет файл, так что при запуске на своей машине останется только
посмотреть `git diff` и закоммитить изменения.

В учебном проекте всё это делает цель Makefile:

```bash
make tut-schema-check
```

Она пересоздаёт учебную базу скриптом схемы и запускает
`cabal run tutorial:generator -- --check`. В настоящем проекте базу
пересоздавать, конечно, не нужно: генератору достаточно базы, к которой
применены все миграции.

Можно поступить и иначе: не хранить `Sch.hs` в репозитории, а генерировать
его в CI прямо перед сборкой. Тогда проверка не нужна, но сборка без базы
становится невозможной. Если же в проекте несколько баз, для каждой
генерируется свой модуль: `updateSchemaFile` вызывается несколько раз с
разными путями, именами модулей и типов схемы.

## Резюме

- `GenNames` задаёт схемы, отдельные таблицы и добавленные связи.
- Таблицы из разных схем базы описываются в одном `Sch.hs`, и связи между
  ними работают как обычно.
- Связь без внешнего ключа добавляется через `AddRelation`, но база её не
  проверяет.
- После миграции нужно перегенерировать `Sch.hs`, и компилятор покажет
  все места, которые нужно исправить.
- В CI генератор с проверкой (`--check`) не даёт забыть о перегенерации.
