# На практике

В учебных примерах у нас была одна схема базы, все связи были объявлены
внешними ключами, а сама схема не менялась. В настоящем проекте всё сложнее:
таблицы бывают разложены по нескольким схемам PostgreSQL, не каждая связь
оформлена внешним ключом, а структура базы меняется с каждой миграцией. В этой
главе мы посмотрим, как `pg-schema` справляется со всем этим и как встроить
генерацию схемы в процесс разработки и в CI.

Примеры этой главы лежат в `tutorial/app/app/Tut/Practice.hs`, а генератор —
в `tutorial/app/generator/Main.hs`. Перед примерами программа пересоздаёт
схему и добавляет двух пользователей, Alice (`id = 1`) и Bob (`id = 2`).

## Что описывает генератор

Какие таблицы и связи попадут в `Sch.hs`, определяет последний аргумент
`updateSchemaFile` — значение типа `GenNames`. У нашего генератора оно такое:

```haskell
--8<-- "app/generator/Main.hs:gen-names"
```

В `schemas` перечисляются схемы базы, все таблицы которых нужно описать. Если
из какой-то схемы нужны только отдельные таблицы, их можно перечислить в
`tables`. Связи между выбранными таблицами генератор находит сам по внешним
ключам, а в `addRelations` можно добавить связи, которых в базе нет. Обо всём
этом по порядку.

## Несколько схем базы

В учебной базе кроме схемы `tut` есть схема `audit` с журналом изменений
проектов:

```sql
--8<-- "sql/00-create-schema.sql:audit"
```

Раз обе схемы перечислены в `GenNames`, таблица `audit.project_log` описана в
том же `Sch.hs`, что и остальные. Аннотация для неё отличается только схемой
базы в имени таблицы, поэтому удобно завести для неё свой синоним:

```haskell
--8<-- "app/app/Tut/Practice.hs:prac-audit-ann"
```

## Связи, которых нет в базе

Иногда связь между таблицами есть по смыслу, но не объявлена внешним ключом.
Так бывает с представлениями (у них внешних ключей не бывает вовсе), с
секционированными таблицами, со старыми базами или когда внешний ключ
сознательно не заводят, например из-за нагрузки. В учебной базе так устроена
колонка `task_events.author_id`: она хранит `id` пользователя, но внешнего
ключа на `users` у неё нет.

Такую связь можно описать в генераторе через `AddRelation`, как в `GenNames`
выше: имя связи, таблица, из которой она ведёт, таблица, в которую она ведёт,
и пары колонок. После этого `pg-schema` работает с ней так же, как с внешним
ключом. Добавленные связи попадают в отдельное пространство имён `_add`, а в
типах результата и в `qPath` их имя, как обычно, проходит через ренеймер.
Прочитаем события вместе с их авторами:

```haskell
--8<-- "app/app/Tut/Practice.hs:prac-event-types"
```

```haskell
--8<-- "app/app/Tut/Practice.hs:prac-addrel"
```

```text
--8<-- "out/tutorial.txt:prac-addrel"
```

сторону, от пользователя к его событиям:

```haskell

```

Комментарий в `GenNames` предупреждает: с добавленными связями нужно быть
осторожным. База ничего о них не знает и не проверяет: в `author_id` может
оказаться `id` несуществующего пользователя, и тогда автор просто не найдётся.
Компилятор проверит, что запросы соответствуют описанию связи, но за то, что
описание соответствует данным, отвечаете вы.

## Когда схема меняется

Самое полезное свойство `pg-schema` проявляется тогда, когда структура базы
меняется. Возьмём для примера миграцию, которая переименовывает колонку и
добавляет обязательную:

```sql
--8<-- "sql/migration-example.sql"
```

После того как миграция применена, нужно перегенерировать `Sch.hs`:

```bash
psql "$PG_CONN" -f tutorial/sql/migration-example.sql
cabal run tutorial:generator
```

Генератор перезапишет файл (старая версия сохранится в `Sch.hs.bak`), а
`git diff` покажет, что именно изменилось в описании базы. Теперь
достаточно собрать проект, и компилятор перечислит все места, которые
миграция сломала. На учебном проекте таких ошибок 42, в пяти модулях. Вот
две из них. В главе 03 мы вставляли проекты без колонки `code`:

```
• We can't insert data because not all mandatory fields are present.
  Table: NameNS "tut" "projects"
  Missing mandatory fields: '["code"]
```

А в главе 04 условие использовало колонку `priority`, которой больше нет:

```
• In schema Sch
  for table "tut" ->> "tasks"
  name "priority" is not defined.

  Valid values are:
    Fields: project_id, seq, title, weight, payload, watchers.
    Foreign key constraints: tasks_project_id_fkey, task_events_project_id_seq_fkey.

  Your source or target type or renaimer is probably invalid.
```

Без `pg-schema` каждая из этих ошибок обнаружилась бы только при выполнении
соответствующего запроса — в тестах, если они его покрывают, или уже в
работе. Здесь же компилятор сразу показывает полный список мест, которые
нужно исправить, и пока он не пуст, программа не соберётся.

Чтобы вернуть учебную базу в исходное состояние, достаточно снова выполнить
`make tut-db-init` и `cabal run tutorial:generator`.

## Проверка в CI

Остаётся убедиться, что `Sch.hs` в репозитории не отстаёт от схемы базы:
кто-то мог добавить миграцию и забыть перегенерировать файл. Для этого
пригодится результат `updateSchemaFile`: он возвращает `True`, если файл
пришлось изменить. Наш генератор принимает флаг `--check` и в этом случае
завершается с ошибкой:

```haskell
--8<-- "app/generator/Main.hs:gen-main"
```

В CI достаточно поднять базу, применить к ней все миграции и запустить
генератор с этим флагом. В учебном проекте для этого есть цель Makefile:

```bash
make tut-schema-check
```

Она пересоздаёт учебную базу и запускает `cabal run tutorial:generator -- --check`.
Если `Sch.hs` устарел, команда завершится с ошибкой, и сборка в CI не пройдёт.
Заодно генератор перезапишет файл, так что при локальном запуске останется
только посмотреть `git diff` и закоммитить изменения.

## Мини-checklist после главы

- [ ] `GenNames` задаёт схемы, отдельные таблицы и добавленные связи.
- [ ] Таблицы из разных схем базы описываются в одном `Sch.hs`, и связи между
      ними работают как обычно.
- [ ] Связь без внешнего ключа добавляется через `AddRelation`, но база её не
      проверяет.
- [ ] После миграции нужно перегенерировать `Sch.hs`, и компилятор покажет
      все места, которые нужно исправить.
- [ ] В CI генератор с проверкой (`--check`) не даёт забыть о перегенерации.
