# Рабочая модель pg-schema

В главе [«Быстрый старт»](01-wow.md) мы прошли весь путь от пустой базы до
чтения связанных данных, многое приняв на веру. Теперь разберём, как
`pg-schema` устроена. Работа с ней состоит из двух этапов. Сначала генератор
читает метаданные PostgreSQL и строит описание схемы базы на уровне типов
Haskell — модуль `Sch.hs`. Затем, при работе с данными, типы входных данных и
результата определяют, какой SQL будет выполнен, а компилятор по описанию
схемы проверяет, что эти типы соответствуют базе. В этой главе мы подробно
посмотрим на оба этапа и увидим, какие ошибки ловит компилятор.

## Генерация описания схемы

Описание схемы создаёт отдельная небольшая программа — генератор. Вот наш
генератор целиком:

```haskell

```

Главное в нём — вызов `updateSchemaFile`. Он подключается к базе, читает
метаданные и записывает описание в файл, если оно изменилось. Какие таблицы
описать, определяет последний аргумент, значение типа `GenNames`:

--8<-- "source/snippets/hs/GenNames.md"

В описание можно включить все таблицы нескольких схем базы, отдельные
таблицы и, если нужно, связи, которых нет в самой базе. Лучше, конечно,
объявлять связи внешними ключами в базе, но это не всегда возможно. В
сгенерированный файл попадут выбранные таблицы с их колонками, все внешние
ключи между ними и все используемые типы, включая перечисления. Подробно о
нескольких схемах, добавленных связях и о том, как встроить генератор в
процесс разработки, рассказывает глава [«На практике»](07-practice.md).

На практике `pg-schema` использовалась со схемами из 30–50 таблиц. Большую
базу имеет смысл описать несколькими схемами `Sch`, и одна таблица может
входить сразу в несколько из них.

## Что лежит в Sch.hs

:mag: _Этот раздел можно пропустить при первом чтении._

Сгенерированный модуль определяет тип `Sch` без значений, который служит
именем схемы на уровне типов, и инстансы нескольких классов для него.
Главный из них — `CSchema`: в нём перечислены все таблицы и все типы данных,
которые в них используются, включая наш enum `project_status`:

--8<-- "source/snippets/hs/CSchema.md"

Оператор `->>` соединяет имя схемы базы с именем таблицы или типа, причём как
на уровне типов, так и на уровне значений. Контекст класса `CSchema`, как и
других классов, описывающих схему, позволяет перевести описание с уровня
типов на уровень значений с помощью `Data.Singletons.demote`: так библиотека
получает имена таблиц и колонок для генерации SQL.

Описание каждой таблицы — её колонки, первичный ключ и уникальные ключи —
задаёт семейство типов `TTabDef`:

--8<-- "source/snippets/hs/CTabDef.md"

Самое важное для проверок — инстанс `CDBFieldInfo`. Он описывает каждое имя,
которое можно использовать вместе с таблицей:

--8<-- "source/snippets/hs/CDBFieldInfo.md"

Каждое имя здесь отнесено к одному из видов. `'RFPlain` — это колонка таблицы,
`'RFFromHere` — внешний ключ из этой таблицы в другую (ссылка на родителя),
`'RFToHere` — внешний ключ из другой таблицы в эту (ссылка на дочерние
строки), а `'RFSelfRef` — ссылка таблицы на саму себя, как `users.manager_id`.
Последнее уравнение для каждой таблицы срабатывает, если имени нет, и выдаёт
ошибку компиляции со списком допустимых имён. Поскольку всё это закрытые
семейства типов, сообщения об ошибках получаются подробными, и мы скоро это
увидим.

Для каждого перечисления в базе генерируется инстанс семейства данных
`PGEnum`. Его конструкторы получаются из имени типа и значений перечисления:

## Аннотация

Каждая операция с данными получает первым аргументом аннотацию `Ann`. Это
значение на уровне типов, и передаётся оно видимым аргументом типа:

--8<-- "source/snippets/hs/Ann.md"

Аннотация содержит четыре вещи. Ренеймер (`annRen`) переводит имена,
которые мы используем в программе, в имена базы. Схема (`annSch`) — это
сгенерированный тип `Sch`. Глубина (`annDepth`) ограничивает вложенность
связей в операциях с деревьями данных и в основном защищает от бесконечных
циклов в типах: обычно хватает 3–5. Наконец, `annTab` — базовая таблица
операции, для операций с деревьями — его корень.

Ренеймер — это функция на уровне типов из имени в программе в имя в базе.
Наш ренеймер переводит имена из camelCase в snake_case, а нескольким именам
связей даёт удобные синонимы:

```haskell
--8<-- "app/app/Tut/Common.hs:renamer"
```

Перевод из camelCase в snake_case библиотека даёт готовым: это семейство
типов `CamelToSnake`. Имена, которые уже записаны в snake_case, оно не
меняет, поэтому с таким ренеймером можно писать имена и так, и так.

Ренеймер, схема и глубина обычно одни и те же для всей программы, поэтому
удобно завести синоним, в котором остаётся только имя таблицы:

```haskell
--8<-- "app/app/Tut/Common.hs:ann"
```

Начнём с простого: вставим пользователя и прочитаем всех пользователей.

примеры этой главы лежат в `tutorial/app/app/Tut/Basics.hs`:

```haskell

```

```text

```

??? note "SQL, отформатированный для чтения"

    ```sql
    --8<-- "out/tutorial.txt:users-generic-sql"
    ```

Мы получили ту же запись, которую добавили, а кроме неё — текст запроса и
его параметры (здесь их нет). Обратите внимание, что тип `User` содержит не
все колонки таблицы `users`: запрос записывает и читает только поля этого
типа. Вид операции определяется структурой входных и выходных данных, и для
этого достаточно инстанса `Generic`. Типы полей и их необязательность при
этом соответствуют типам колонок и тому, допускают ли они `NULL`.

### :thinking_face: Что будет, если ошибиться?

Посмотрим, как компилятор реагирует на ошибки в этом примере. Если
опечататься в имени таблицы и написать `MyAnn "Users"`, сообщение будет
коротким:

```
• In schema Sch.Sch the table NameNS "tut" "Users" is not defined.
```

Имя схемы здесь записано как `Sch.Sch`, потому что модуль с примером
импортирует `Sch` без единого имени (`import Sch ()`), и GHC указывает тип
вместе с модулем. Если же переименовать
поле `email` в `mail`, компилятор перечислит все колонки и связи таблицы
`users`:

```
• In schema Sch.Sch
  for table "tut" ->> "users"
  name "mail" is not defined.

  Valid values are:
    Fields: id, name, email, manager_id, created_at.
    Foreign key constraints: users_manager_id_fkey, task_events_author, projects_owner_id_fkey.

  Your source or target type or renamer is probably invalid.
```

Проверяется и обязательность колонок. Колонка `name` объявлена `NOT NULL`,
поэтому `name :: Maybe Text` не скомпилируется:

```
• You can't use Maybe for mandatory fields

  Table: NameNS "tut" "users"
  DB Field name: "name"
  DB Field type: NameNS "pg_catalog" "text"
  Haskell Field type: Maybe Text
```

А колонка `email` допускает `NULL`, поэтому без `Maybe` тоже ничего не
выйдет:

```
• You have to use Maybe for nullable fields

  Table: NameNS "tut" "users"
  DB Field name: "email"
  DB Field type: NameNS "pg_catalog" "text"
  Haskell Field type: Text
```

Наконец, если тип поля просто не подходит к типу колонки, например
`email :: Maybe Int`, сообщение получается менее дружелюбным:

```
• Could not solve: ‘CanConvert1
                      Sch.Sch
                      (NameNS "tut" "users")
                      "email"
                      (NameNS "pg_catalog" "text")
                      (TypDef "S" Nothing '[])
                      Int’
    arising from a use of ‘insertSch_’
```

Но и его можно прочитать: в схеме `Sch` у таблицы `tut.users` колонка
`email` имеет тип `pg_catalog.text`, и преобразования в `Int` для неё нет.
Какие типы Haskell подходят к каким типам PostgreSQL, сведено в
[справочнике](appendix-reference.md#types).

## PgTag

Record-типы удобны, но не всегда: заводить отдельный тип ради пары полей
утомительно, а одинаковые имена полей в разных типах требуют расширения
`DuplicateRecordFields`. Поэтому в `pg-schema` есть вторая нотация —
`PgTag`, поле с именем на уровне типов:

--8<-- "source/snippets/hs/PgTag.md"

`PgTag` похож на известный тип `PgTagged`, но у него другие инстансы. Для
удобства есть оператор `(:=)` на уровне типов и `(=:)` на уровне значений.
Отдельные поля соединяются оператором `(:.)` из `postgresql-simple`, а
вперемешку с ними можно использовать и Generic-рекорды. Вставим двух
пользователей и попросим вернуть их `id`, `manager_id` и поля типа `User`:

```haskell
--8<-- "app/app/Tut/Basics.hs:users-pgtag"
```

```text
--8<-- "out/tutorial.txt:users-pgtag"
```

??? note "SQL, отформатированный для чтения"

    ```sql
    --8<-- "out/tutorial.txt:users-pgtag-sql"
    ```

Здесь `insertSch` возвращает результат вставки (`insert … returning`), и
набор колонок в `returning` определяется типом результата. Обратите внимание,
что мы пишем `managerId`, а не `manager_id`: имена полей проходят через
ренеймер. Если же написать `managerId1`, компилятор сообщит, что поля нет,
и назовёт его уже после ренеймера, `manager_id1`:

```
• In schema Sch.Sch
  for table "tut" ->> "users"
  name "manager_id1" is not defined.

  Valid values are:
    Fields: id, name, email, manager_id, created_at.
    Foreign key constraints: users_manager_id_fkey, task_events_author, projects_owner_id_fkey.

  Your source or target type or renamer is probably invalid.
```

## Резюме

- Генератор строит по базе модуль `Sch.hs`: таблицы, колонки, ключи, связи и
  перечисления на уровне типов.
- Каждая операция получает аннотацию `Ann`: ренеймер, схему, глубину и
  базовую таблицу.
- Ренеймер переводит имена из программы в имена базы; в сообщениях об
  ошибках имена уже переведены.
- SQL операции определяется типами входных данных и результата, а
  компилятор проверяет их по описанию схемы: имена, обязательность и типы
  колонок.
- Данные можно описывать Generic-рекордами, полями `PgTag` или смешивать
  обе нотации.
