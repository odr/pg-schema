# Изменение связанных данных

В главе [«Изменение данных в одной таблице»](03-flat-dml.md) каждая операция
работала с одной таблицей. Но данные часто приходят целым деревом: проект
вместе с задачами, а задачи вместе с событиями. Записывать такое дерево по
частям неудобно: нужно вставить проект, узнать его `id`, подставить его в
задачи, вставить их и так далее. `pg-schema` умеет записать всё дерево одной
операцией. Для этого есть три функции: `insertJSON` вставляет новые данные,
`upsertJSON` вставляет новые и изменяет существующие, а `updateJSON` только
изменяет. У каждой есть вариант с подчёркиванием (`insertJSON_` и так далее),
который ничего не возвращает из базы.

Все три функции устроены одинаково, и мы уже видели это в главе
[«Быстрый старт»](01-wow.md). По типам входных данных и результата
`pg-schema` генерирует временную функцию на plpgsql, создаёт её в базе,
вызывает, передав всё дерево одним параметром типа `jsonb`, и удаляет. Это
три команды, и сколько бы строк ни было в дереве, их число не меняется. Если
транзакция ещё не открыта (это видно по состоянию соединения), всё это
выполняется в отдельной транзакции, так что дерево записывается целиком или не
записывается вовсе.

Примеры этой главы лежат в `tutorial/app/app/Tut/TreeDml.hs`. Перед ними
программа пересоздаёт схему и добавляет одного пользователя с `id = 1`,
владельца всех проектов.

## Вставка: insertJSON

Входные данные опишем типами. Дочерние строки — это поля со списком строк,
названные по имени внешнего ключа. Как и в главах 01 и 04, это имя
ограничения в базе (`tasks_project_id_fkey`, `task_events_project_id_seq_fkey`),
прошедшее через ренеймер `MyRenamer`, поэтому мы пишем его в camelCase:

```haskell
--8<-- "app/app/Tut/TreeDml.hs:tree-types"
```

В типе задачи нет колонки `project_id`, а в типе события — колонок
`project_id` и `seq`, хотя все они обязательны. Их значения берутся из
родительской строки: `insertJSON` сначала вставляет проект, получает его `id`
и подставляет его в задачи, а затем так же поступает с событиями. Поэтому
`insertJSON` требует во входных данных все обязательные колонки, кроме тех,
что приходят из связи с родителем, и тех, у которых есть значение по
умолчанию. Если обязательной колонки не хватает, программа не скомпилируется,
так же как с `insertSch` в главе 03.

Сами деревья удобно строить функцией `rowsOf`. Она похожа на `named` из
главы 03, но `named` получает имена полей списком строк, а `rowsOf` берёт и
имена, и типы полей из типа строки, который передаётся ей как
`rowsOf @ProjectIn`. Поэтому значения можно писать без имён
и без аннотаций типов, а дочерние строки — просто вложенными списками.

Как и в плоских операциях, тип результата задаёт, что вернуть после вставки.
Вернём ключи всех вставленных строк, на всех трёх уровнях:

```haskell
--8<-- "app/app/Tut/TreeDml.hs:tree-keys"
```

```haskell
--8<-- "app/app/Tut/TreeDml.hs:tree-insert"
```

```text
--8<-- "out/tutorial.txt:tree-insert"
```

??? note "SQL, отформатированный для чтения"

    ```sql
    --8<-- "out/tutorial.txt:tree-insert-sql"
    ```

В типе результата могут быть любые колонки таблиц, в том числе те, которых не
было во входных данных, как `id` проекта. А вот ветки результата должны быть
среди веток входных данных: вернуть задачи можно только тогда, когда мы их
вставляли. Это, как и остальные правила для типа результата, проверяется при
компиляции.

`insertJSON_` делает то же самое, но ничего не возвращает из базы. Вместо
функции он создаёт временную процедуру, а в программу возвращает только
сгенерированный SQL. Если результат не нужен, это немного экономит работу:
базе не приходится собирать ответ в `jsonb`, а программе — разбирать его.


## Вставка или изменение: upsertJSON

`insertJSON` только вставляет. Если строка с таким ключом уже есть, PostgreSQL
сообщит о нарушении уникальности, и вся операция будет отменена. Когда же
данные могут быть как новыми, так и уже существующими, нужен `upsertJSON`. Что
делать со строками, он решает для каждого уровня дерева (то есть для каждой
таблицы) по полям его типа, и решает это при компиляции:

- если в типе есть ключ, но есть не все обязательные колонки, строки
  изменяются по этому ключу (`update`);
- если есть и ключ, и все обязательные колонки, строки вставляются, а при
  конфликте по ключу изменяются (`insert … on conflict … do update`);
- если есть все обязательные колонки, но нет ключа, строки просто
  вставляются (`insert`);
- если нет ни ключа, ни всех обязательных колонок, программа не
  скомпилируется: со строкой нечего делать.

Обязательные колонки здесь те же, что для `insertJSON`: `NOT NULL` без
значения по умолчанию, кроме тех, что приходят от родителя. Ключом считается
первичный ключ, а если его колонок в типе нет — уникальный ключ, все колонки
которого есть в типе. Сначала рассматриваются уникальные ключи из
`NOT NULL`-колонок, а ключи с nullable-колонками — только если первых в
таблице нет.
Колонки, которые приходят от родителя, тоже считаются. После родительской
строки так же обрабатываются её дочерние строки. Изменим
проект 1: переименуем его первую задачу, добавим ей событие и добавим проекту
новую задачу:

```haskell
--8<-- "app/app/Tut/TreeDml.hs:tree-patch-types"
```

```haskell
--8<-- "app/app/Tut/TreeDml.hs:tree-upsert"
```

```text
--8<-- "out/tutorial.txt:tree-upsert"
```

??? note "SQL, отформатированный для чтения"

    ```sql
    --8<-- "out/tutorial.txt:tree-upsert-sql"
    ```

Корень здесь — только ключ проекта, поэтому проект изменяется по `id` (менять
в нём нечего, но найти его нужно, чтобы дойти до задач). У задач есть ключ
`(project_id, seq)`, где `project_id` приходит от проекта, и все обязательные
колонки: `title` мы передали, а у `priority` есть значение по умолчанию.
Поэтому для задач выполняется `insert … on conflict`: задача 1 уже была, и у
неё изменилось название, а задачи 3 не было, и она вставилась. При конфликте
изменяются только колонки, которые есть в типе, поэтому приоритет задачи 1
остался прежним. Так же вставилось и новое событие.

Обратите внимание на тип результата `PatchOut`: корень в нём обёрнут в
`Maybe`, а задачи — нет. Проект изменяется по ключу (`update`) и может не
найтись, а задачи идут через `insert … on conflict`, и строка задачи после
этого есть всегда. Поэтому `Maybe` нужен только там, где выполняется
`update`. Если строка не нашлась, на её месте в результате будет `Nothing`,
а её дочерние строки обрабатываться не будут:

```haskell
--8<-- "app/app/Tut/TreeDml.hs:tree-upsert-missing"
```

```text
--8<-- "out/tutorial.txt:tree-upsert-missing"
```

Проекта 999 нет, и задача «Ghost» не вставилась. Где в результате
`upsertJSON` обязателен `Maybe`, а где запрещён, сведено в таблицу в
[справочнике](appendix-reference.md#returning).

## Изменение: updateJSON

`updateJSON` никогда ничего не вставляет: каждую строку дерева он изменяет по
ключу. Поэтому ключ нужен на каждом уровне, а вот обязательные колонки — нет.
Переведём проект 2 в статус `active`, изменим приоритет его задачи 1 и
попробуем изменить несуществующую задачу 9 и несуществующий проект 999:

```haskell
--8<-- "app/app/Tut/TreeDml.hs:tree-update-types"
```

```haskell
--8<-- "app/app/Tut/TreeDml.hs:tree-update"
```

```text
--8<-- "out/tutorial.txt:tree-update"
```

??? note "SQL, отформатированный для чтения"

    ```sql
    --8<-- "out/tutorial.txt:tree-update-sql"
    ```

Результат показывает судьбу каждой строки. Проект 2 найден, и в его списке
задач первая изменилась, а вместо задачи 9 стоит `Nothing`. Проекта 999 нет, и
вместо него тоже `Nothing`. Списки результата идут в том же порядке, что и
входные данные, так что каждый `Nothing` легко сопоставить с тем, что не
нашлось. Не найтись может любая строка, поэтому в типе результата `updateJSON`
в `Maybe` должны быть обёрнуты и корень, и элементы дочерних списков.

Если в какой-то строке дерева ключа нет, изменить её не по чему, и программа
не скомпилируется. Уберём, например, `seq` из типа задачи:

```
• We can't upsert data because for table NameNS "tut" "tasks"
  not all mandatory fields are present and no full primary or
  unique key is covered by record fields.
  Missing mandatory fields: ["seq", "title"]
  Possible keys: '[["project_id", "seq"]]
```

Сообщение общее для `upsertJSON` и `updateJSON`, поэтому в нём говорится об
upsert и об обязательных колонках. Для `updateJSON` важна последняя строка:
список ключей, один из которых должен целиком быть в типе. Колонка
`project_id` придёт от проекта, так что для задач не хватает `seq`.

## Транзакции

Как мы уже говорили, каждая из этих операций сама открывает транзакцию, если
она ещё не открыта, и при ошибке ничего частично записанного не остаётся. Если
же транзакция уже открыта, операция выполняется внутри неё и подчиняется ей:
при откате внешней транзакции откатится и всё, что записала операция. Это
позволяет объединять несколько операций в одну транзакцию. В следующем
примере мы дважды вставляем проект с одним и тем же `id` внутри
`withTransaction` из `postgresql-simple`:

```haskell
--8<-- "app/app/Tut/TreeDml.hs:tree-tx"
```

```text
--8<-- "out/tutorial.txt:tree-tx"
```

Вторая вставка нарушила уникальность, и `withTransaction` откатил всю
транзакцию, включая первую, успешную вставку. Проекта «Tx demo» в базе нет.
Для подсчёта мы использовали агрегат из главы 04:

## Резюме

- `insertJSON` вставляет дерево одной операцией, а колонки, которые
  приходят из связи с родителем, указывать не нужно.
- Ветки результата должны быть среди веток входных данных, колонки —
  любые.
- `upsertJSON` по полям типа выбирает для каждого уровня `update`,
  `insert … on conflict` или `insert`.
- `updateJSON` никогда не вставляет и требует ключ на каждом уровне.
- Ненайденные строки дают `Nothing` на своём месте в результате.
- Операции выполняются в транзакции и подчиняются внешней транзакции.
