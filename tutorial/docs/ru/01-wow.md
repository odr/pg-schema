# Быстрый старт

Цель: с нуля создать учебную БД, сгенерировать описание схемы и одним
запросом вставить и прочитать дерево «проект → задачи». Имена таблиц, полей и
связей при этом проверяет компилятор.

## Подготовка

Все команды выполняются из корня репозитория `pg-schema` (там, где лежат
`cabal.project` и `Makefile`).

### Строка соединения

Генератор и приложение берут строку соединения из переменной `PG_CONN`.
Учебная БД называется `tutorial`:

```bash
export PG_CONN='dbname=tutorial'
```

Если PostgreSQL требует хост, пользователя или пароль, добавьте их в эту
строку, например `dbname=tutorial host=localhost user=postgres`.
Без `PG_CONN` приложение подключается к `dbname=tutorial`, а генератор
ничего не делает.

### Учебная схема

```bash
make tut-db-init
```

Команда создаёт БД `tutorial`, если её ещё нет, и применяет
`tutorial/sql/00-create-schema.sql`. Скрипт сначала удаляет схему `tut`,
так что повторный запуск даёт чистую БД.

Проверка:

```bash
psql "$PG_CONN" -c "\dt tut.*"
```

Ожидаем таблицы: `users`, `projects`, `tasks`, `task_events`.

:bulb: Первая сборка с нуля долго собирает зависимости. Её удобно запустить
заранее, пока вы читаете дальше: `cabal build tutorial:tutorial`.

## Генерация схемы

Генератор `tutorial/app/generator/Main.hs` вызывает `updateSchemaFile` и
пишет модуль схемы в `tutorial/app/app/Sch.hs`:

```bash
cabal run tutorial:generator
```

Проверка, что файл появился или обновился:

```bash
ls -la tutorial/app/app/Sch.hs
```

### Запуск примеров

```bash
cabal run tutorial:tutorial
```

В выводе — примеры всех глав. Примеры этой главы идут первыми, их разбор — ниже.

Шаги 1–3 одной командой (вывод сохраняется в `tutorial/out/tutorial.txt`):

```bash
make tut-run
```

Что именно лежит в `Sch.hs`, разобрано в главе
[«Рабочая модель pg-schema»](02-core-workflow.md). Здесь достаточно знать, что
это type-level описание таблиц, полей и связей схемы `tut`.

## Описание данных

Код примеров главы — в `tutorial/app/app/Tut/Wow.hs`. Он использует такие
расширения:

```haskell
--8<-- "app/app/Tut/Wow.hs:extensions"
```

`BlockArguments` нужен для `qRoot do …`, а `DuplicateRecordFields` — потому
что поле `title` есть и у проекта, и у задачи.

Любая операция начинается с аннотации `Ann`. Она говорит, с какой таблицей
мы работаем и как сопоставлять имена Haskell с именами в БД:

```haskell
--8<-- "app/app/Tut/Wow.hs:ann"
```

Здесь `RenamerId` — имена не преобразуются, поля Haskell называются так же,
как колонки в БД. `Sch` — сгенерированная схема, `3` — допустимая глубина
вложенности дерева. Подробнее об `Ann` и ренеймерах — в главе 02.

Данные описываем обычными record-типами с `Generic`:

```haskell
--8<-- "app/app/Tut/Wow.hs:types"
```

Обратите внимание на поле `tasks_project_id_fkey`. Это имя внешнего ключа
`tasks.project_id → projects.id`, и по нему `pg-schema` понимает, что в поле
лежат дочерние строки из `tasks`. Тип `PGEnum Sch ("tut" ->> "project_status")`
сгенерирован из enum в БД, его значения — `Project_status_draft`,
`Project_status_active`, `Project_status_archived`.

## Вставка дерева

У проекта обязателен владелец (`projects.owner_id`), поэтому сначала
вставим пользователя:

```haskell
--8<-- "app/app/Tut/Wow.hs:wow-owner"
```

`Owner` — record с одним полем `name`:

```haskell
--8<-- "app/app/Tut/Wow.hs:owner-type"
```

Теперь два проекта с задачами — одним вызовом `insertJSON`:

```haskell
--8<-- "app/app/Tut/Wow.hs:wow-insert"
```

Какие колонки вернуть после вставки, определяет тип результата. Здесь это
ключи проекта и его задач:

```haskell
--8<-- "app/app/Tut/Wow.hs:key-types"
```

Вывод — ключи вставленных строк и текст запроса:

```text
--8<-- "out/tutorial.txt:wow-insert"
```

`insertJSON` передаёт всё дерево в PostgreSQL одним параметром `jsonb`, а
вставку выполняет сгенерированная функция на plpgsql. Обратите внимание:
`project_id` задач мы не передавали — он берётся из только что вставленного
проекта.

## Чтение дерева

Запрос описываем отдельно — так его можно и выполнить, и посмотреть его SQL:

```haskell
--8<-- "app/app/Tut/Wow.hs:query"
```

`qRoot` задаёт условия для корневой таблицы `projects`, а `qPath` — для
ветки задач: только задачи с приоритетом меньше 50, по порядку `seq`.
Выполняем запрос и читаем результат в тот же тип `Project`, которым вставляли:

```haskell
--8<-- "app/app/Tut/Wow.hs:wow-select"
```

```text
--8<-- "out/tutorial.txt:wow-select"
```

Проект «Mobile app» не попал в результат — он в статусе `draft`. У проекта
«Website» нет задачи «Nice to have»: её приоритет 100. Всё дерево
прочитано одним SQL-запросом, задачи собраны в JSON-массив внутри него.
